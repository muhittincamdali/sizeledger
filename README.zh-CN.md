把 sizeledger 指向一个 `.ipa`、`.app` 或 `.xcarchive`，它就会告诉你应用的字节都用在了哪里：按类别、按
framework 和资源、按语言以及按 CPU 架构。它只读取文件，不会构建、运行、上传或修改任何内容，在 macOS 和
Linux 上的表现完全一致。

## 亮点

- **整个应用只看一张表。** 主可执行文件、framework 和 dylib、App Extension、App Clip、watch 应用、本地化、asset catalog、代码签名以及其他所有内容。各类别之和始终等于总大小。
- **每个 framework 和 extension 各占一行**，每种 `.lproj` 语言则在整个应用及其 framework 范围内汇总。
- **每个二进制文件的架构切片**：哪些二进制文件是 universal，每个切片占多大；段（segment）大小和 Swift
  metadata 在 JSON 中给出。
- **三种大小分开列出**：文件大小之和、安装大小估算值（按 APFS 的存储方式，以完整的 4 KiB 块计）以及
  `.ipa` 的压缩大小。sizeledger 不声称知道 App Store 的下载大小；
  [原因见这里](docs/guides/why-install-size-is-an-estimate.md)。
- **既给人看，也给 CI 用**：终端表格、可用于 pull request 或作业摘要的 Markdown，以及键顺序固定的 JSON
  报告，你可以提交它、用 `jq` 处理并进行比较。
- **同时是一个 Swift 库**：[SizeLedgerKit](https://muhittincamdali.github.io/sizeledger/) 把同样的报告交给你自己的工具。没有任何依赖：ZIP 读取器、DEFLATE 解码器和 Mach-O 解析器都包含在其中。

## 快速开始

**1. 安装**（macOS 或 Linux，使用 [Homebrew](https://brew.sh)）：

```sh
brew install muhittincamdali/tap/sizeledger
```

如果不使用 Homebrew，请使用
[发布的二进制文件或从源码构建](#安装)。

**2. 测量你的应用。** 以下任意一种都可以：导出的 `.ipa`、构建产生的 `.app`，或通过
**Product › Archive** 得到的 `.xcarchive`。

```sh
sizeledger analyze path/to/MyApp.ipa
```

**3. 阅读表格。** "By category" 说明哪类内容占得多；"Largest items" 列出具体的文件、framework 和文件夹；
"Binaries" 显示哪些二进制文件包含不止一种架构。末尾的注释会指出哪些数字需要结合上下文理解（例如模拟器构建）。用 `--out size/main.json` 保存完整报告，以便留存或日后比较。

[阅读你的第一份大小分析](docs/guides/read-your-first-breakdown.md)会逐行讲解一份真实的报告。

| 带 DocC 文档的 SizeLedgerKit 库                                                                        | 可用          |

| 用 YAML 编写的 `budget` 规则（按路径、总量、App Clip 上限），以退出码 1 表示超限，并提供 GitHub Action | 计划中（0.3） |

| Android `.apk` 和 `.aab`                                                                               | 计划中（1.1） |

在 `budget` 出现之前，CI 中的上限检查只需一行 `jq`；参见

## 使用方法

```text
sizeledger analyze <input> [--format tty|markdown|json] [--out <file>] [--force] [--top <n>] [--color auto|always|never] [--quiet]
                    [--max-files <n>] [--max-bytes <bytes>] [--max-ratio <ratio>] [--max-depth <n>]
```

| 选项               | 作用                                                           |
| ------------------ | -------------------------------------------------------------- |
| `<input>`          | 一个 `.app` 文件夹、一个 `.ipa` 文件或一个 `.xcarchive` 文件夹 |
| `-f, --format`     | 输出什么：`tty`（默认，表格）、`markdown` 或 `json`            |
| `-o, --out <file>` | 同时把 JSON 报告写入新文件；缺少的文件夹会被创建。只有指向设备或管道（如 `/dev/stdout`）时才会跟随符号链接 |
| `--force`          | `--out` 文件已存在时替换它；不加此选项时保留已有文件，退出状态为 2 |
| `--top <n>`        | 列出多少个条目、语言和二进制文件（默认 10）                    |
| `--color`          | `auto` 仅在终端中使用颜色，并且在设置了 `NO_COLOR` 时不使用    |
| `-q, --quiet`      | 不输出任何内容（与 `--out` 配合使用）                          |

退出状态：报告生成成功时为 `0`；无法读取输入或无法写入报告时为 `2`（标准错误输出中会有一行说明原因）；选项无效时为 `64`。`1` 留给计划中的 `budget` 命令。

```sh
# Keep the report for later
sizeledger analyze build/MyApp.ipa --out size/main.json

# Markdown in a GitHub Actions job summary
sizeledger analyze build/MyApp.xcarchive --format markdown >> "$GITHUB_STEP_SUMMARY"

# The ten biggest files anywhere in the bundle (bytes and file name)
jq -r '[.tree | .. | objects | select(has("children") | not)] | sort_by(-.bytes) | .[:10][] | "\(.bytes)\t\(.name)"' size/main.json
```

`jq -r` 会原样输出应用中的名称，包括 JSON 文件中转义过的双向控制字符；对于不信任的应用，请去掉 `-r`。

JSON 的结构在 [DocC 文章](https://muhittincamdali.github.io/sizeledger/documentation/sizeledgerkit/jsonlayout)中有说明；
[Fixtures/snapshots](Fixtures/snapshots) 中有完整的报告。

## 三种大小

| 大小                                     | 含义                                                      | SampleShop 2.0 的数值 |
| ---------------------------------------- | --------------------------------------------------------- | --------------------- |
| 总计（`bytes`）                          | 文件大小之和，即文件管理器显示的数值                      | 8.75 MB               |
| 安装大小，估算（`installBytes`）         | 每个文件向上取整到完整的 4 KiB 块，与 APFS 的存储方式一致 | 8.80 MB               |
| `.ipa` 中的压缩大小（`compressedBytes`） | 包内文件在归档中占用的大小；仅适用于 `.ipa` 输入          | 2.72 MB               |

它们都不是 App Store 的下载大小或安装大小：App Store 会针对每台设备对应用进行瘦身（thinning）、加密二进制文件并压缩下载内容。这些数字可以从 Xcode 的 App Thinning Size Report 和 App Store Connect 获得。
sizeledger 给出的是仅凭文件就能在任何机器上、对每一次构建都得到的数字。
[为什么安装大小只是估算](docs/guides/why-install-size-is-an-estimate.md)有详细说明，
[App Clip 大小限制](docs/guides/app-clip-size.md)则把这些数字应用到 App Clip 上。

## 如何测试

- **与 `du` 对照**，这是 v0.1 的验收检查，使用从 `.ipa` 解包出来的两个 SampleShop 版本。在 Mac（Apple
  silicon，macOS 27.0.1，APFS）上，安装大小估算值与 `du -sk` 完全一致，总计与 `du -A` 相差在 0.16% 以内；在 Linux 容器（swift:6.4.1-noble，aarch64）中，总计与 `du -b --apparent-size` 一致，安装大小估算值与
  `du -sk` 相差在 0.65% 以内（那里的 `du -sk` 还会为每个文件夹多算 4 KiB）。两种环境下，误差超过 1% 时测试都会失败。
- **快照**：两个版本的 JSON、文本和 Markdown 报告都已提交；同样的快照在 macOS 和 Linux 上都能通过。
- **真实的应用**：SampleShop 由[一个脚本](Fixtures/scripts/build-sample-app.sh)使用 `swiftc`、`actool` 和
  `codesign` 构建，并在 iOS 27.0 模拟器中运行：

    <picture><source media="(prefers-color-scheme: dark)" srcset="docs/media/sampleshop-ios27-simulator-dark.png"><source media="(prefers-color-scheme: light)" srcset="docs/media/sampleshop-ios27-simulator-light.png"><img src="docs/media/sampleshop-ios27-simulator-light.png" alt="iOS 27 Simulator 中的 SampleShop 2.0：一个 banner 和一个带图片与价格的商品列表" width="240"></picture>

- **对照参考实现检验的读取器**：DEFLATE 解码器对照 zlib 的输出，覆盖 stored、fixed 和 dynamic 块；
  Mach-O 解析器覆盖 thin、32 位、fat 和 fat64 文件；还有 ZIP64、损坏的归档，以及包含终端转义序列的文件名。

共有 159 个测试，由 CI 在 macOS 和 Linux（x86_64 和 arm64）上运行；其中一个需要 APFS 不接受的非 UTF-8 文件名，因此只在 Linux 上运行。使用 release 构建测量 SampleShop 2.0（包括进程启动），在一台正忙于其他工作的 Mac（Apple silicon，负载平均值 41 到 136）上，三组各 21 次运行的中位数为 14.4 到 17.4 ms；耗时取决于机器上同时运行的其他任务。[scripts/bench.sh](scripts/bench.sh) 可以重复这一测量。

## 局限

- 大小是本地测量值。App Store 的下载和安装大小取决于 Apple 一侧的瘦身、加密和压缩，因此 sizeledger
  报告的是估算值，并明确说明这一点。
- Asset catalog（`Assets.car`）按文件计算；其中的 rendition 暂不列出（计划在 0.8 中通过 macOS 上的
  `assetutil` 实现）。
- Swift metadata 的大小是 `__swift5_*` 段的大小，是一个下限：部分 metadata 位于 `__const` 中。
- iOS 风格的 bundle（iOS、iPadOS、tvOS、watchOS、visionOS）会被分类。带有 `Contents/` 文件夹的 macOS
  `.app` 会被测量，但其中的文件会归入 "Other resources"。
- 包含多个应用、带加密条目、使用 stored 和 DEFLATE 以外压缩方式，或条目路径中含有 `..` 的 `.ipa`，会被拒绝并给出提示信息，而不是靠猜测处理。
- 路径按字节比较，与解压工具和文件系统看到的一致：只在 Unicode 规范化（NFC 与 NFD）上不同的两个名称是两个文件，后面跟着组合字符的 `/` 仍然分隔两个文件夹。不是有效 UTF-8 的名称按 Latin-1 读取显示，但仍按存储的字节区分，所以 `caf\xE9.bin` 和 UTF-8 的 `café.bin` 是读起来相同的两个文件；报告列出这类名称时会附加一条说明。
- 为了读取压缩的 `.ipa` 条目中靠后的 Mach-O 头，sizeledger 会解压它之前的全部内容，但只保留 32 KiB 的窗口，因此恶意构造的条目只会耗费时间，而不会耗费内存：在 Mac（Apple silicon）上每解压 1 GB 约需 1 s。
- 输入不可信，因此精心构造或损坏的输入不会耗尽内存或栈，所用时间则受下列上限约束。条目共享已存储字节的
  `.ipa`（重叠式 zip 炸弹）会被视为损坏而拒绝。在默认上限内找到的最慢的构造 `.ipa` 是一个 28.6 MB 的文件，
  含两个各声明 4.29 GB、Mach-O 头位于末尾的条目，在一台正忙于其他工作的 Mac（Apple silicon）上耗时 15 到
  24 s；调低 `--max-bytes` 可降低这一上限。sizeledger 会拒绝以下输入：文件超过
  500,000 个、路径嵌套深度超过 64 层、`.ipa` 声明的未压缩字节超过 8 GiB，或某个 `.ipa` 条目解压后超过其
  存储大小 300 倍（zip 炸弹）；可用 `--max-files`、`--max-depth`、`--max-bytes` 和 `--max-ratio` 调高这些
  上限。为保证 JSON 报告总能写出，`--max-depth` 最多为 100；文件夹不会被解压，因此 `--max-bytes` 只适用于
  `.ipa`。损坏的 Mach-O 或 ZIP 头会给出 "unreadable" 提示或退出状态为 2 的明确错误，绝不崩溃。重复的条目
  路径只计一次。
