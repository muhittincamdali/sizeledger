Aponte o sizeledger para um `.ipa`, um `.app` ou um `.xcarchive` e ele mostra onde estão os bytes do app:
por categoria, por framework e recurso, por idioma e por arquitetura de CPU. Ele só lê os arquivos; não
compila, não executa, não envia nem altera nada, e funciona do mesmo jeito no macOS e no Linux.

<sub>Gravado a partir do comando real (<code>node scripts/demo.mjs</code>) no
<a href="Fixtures/README.md">SampleShop 2.0</a>, um app SwiftUI que este repositório compila para o iOS
Simulator. A saída é a mesma em um Mac (Apple silicon) e nas imagens de CI do Linux.</sub>

## Destaques

- **Uma tabela para o app inteiro.** Executável principal, frameworks e dylibs, extensões do app,
  App Clips, app de watch, localizações, asset catalogs, assinatura de código e todo o resto. As
  categorias sempre somam o total.
- **Cada framework e cada extensão em sua própria linha**, e cada idioma `.lproj` somado no app inteiro
  e em seus frameworks.
- **Slices de arquitetura de cada binário**: quais binários são universais e quanto cada slice ocupa;
  os tamanhos dos segmentos e os metadados do Swift vão no JSON.
- **Três tamanhos separados**: a soma dos arquivos, uma estimativa do tamanho de instalação (blocos
  inteiros de 4 KiB, como o APFS armazena) e, para um `.ipa`, o tamanho comprimido. O sizeledger não
  afirma saber o tamanho de download da App Store;
  [veja o motivo](docs/guides/why-install-size-is-an-estimate.md).
- **Para pessoas e para CI**: uma tabela no terminal, Markdown para um pull request ou para o resumo de
  um job e um relatório JSON com ordem de chaves estável, que você pode commitar, consultar com `jq` e
  comparar.
- **Também uma biblioteca Swift**: o [SizeLedgerKit](https://muhittincamdali.github.io/sizeledger/)
  entrega o mesmo relatório às suas próprias ferramentas. Sem dependências: o leitor de ZIP, o
  decodificador DEFLATE e o parser de Mach-O fazem parte dele.

## Início rápido

**1. Instale** (macOS ou Linux com [Homebrew](https://brew.sh)):

```sh
brew install muhittincamdali/tap/sizeledger
```

Sem Homebrew, use um
[binário da release ou compile a partir do código-fonte](#instalação).

**2. Meça seu app.** Qualquer um destes serve: um `.ipa` exportado, o `.app` de um build ou um
`.xcarchive` de **Product › Archive**.

```sh
sizeledger analyze path/to/MyApp.ipa
```

**3. Leia a tabela.** "By category" diz que tipo de conteúdo pesa mais; "Largest items" nomeia os
arquivos, frameworks e pastas; "Binaries" mostra quais carregam mais de uma arquitetura. As notas no
final avisam quando um número precisa de contexto (por exemplo, um build para simulador). Salve o
relatório completo com `--out size/main.json` para guardá-lo ou compará-lo depois.

[Leia seu primeiro detalhamento](docs/guides/read-your-first-breakdown.md) percorre um relatório real
linha por linha.

## Instalação

| Método                   | Comando                                                                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Homebrew (macOS, Linux)  | `brew install muhittincamdali/tap/sizeledger`                                                                                                                                                                                    |
| Binário da release       | Baixe `sizeledger-<version>-macos-universal.tar.gz` ou `-linux-x86_64` / `-linux-aarch64` em [Releases](https://github.com/muhittincamdali/sizeledger/releases), confira com `SHA256SUMS` e coloque o `sizeledger` no seu `PATH` |
| A partir do código-fonte | `git clone https://github.com/muhittincamdali/sizeledger.git && cd sizeledger && swift build -c release` (o binário fica em `.build/release/sizeledger`)                                                                         |
| Swift package            | `.package(url: "https://github.com/muhittincamdali/sizeledger", from: "0.1.5")`, product `SizeLedgerKit`                                                                                                                         |

Para compilar, é preciso Swift 6.2 ou mais recente (Xcode 26 ou mais recente em um Mac). Os binários de
release para Linux trazem o runtime do Swift e exigem glibc 2.35 ou mais recente (Ubuntu 22.04,
Debian 12 ou mais novos).

## Uso

```text
sizeledger analyze <input> [--format tty|markdown|json] [--out <file>] [--top <n>] [--color auto|always|never] [--quiet]
                    [--max-files <n>] [--max-bytes <bytes>] [--max-ratio <ratio>] [--max-depth <n>]
```

| Opção              | O que faz                                                                       |
| ------------------ | ------------------------------------------------------------------------------- |
| `<input>`          | Uma pasta `.app`, um arquivo `.ipa` ou uma pasta `.xcarchive`                   |
| `-f, --format`     | O que imprimir: `tty` (padrão, uma tabela), `markdown` ou `json`                |
| `-o, --out <file>` | Grava também o relatório JSON em um arquivo; pastas que não existem são criadas |
| `--top <n>`        | Quantos itens, idiomas e binários listar (padrão 10)                            |
| `--color`          | `auto` usa cores somente em um terminal e não quando `NO_COLOR` está definida   |
| `-q, --quiet`      | Não imprime nada (com `--out`)                                                  |

Código de saída: `0` quando o relatório foi gerado, `2` quando a entrada não pôde ser lida ou o
relatório não pôde ser gravado (uma linha na saída de erro padrão diz o motivo) e `64` para opções
inválidas. O `1` está reservado para o comando `budget`, que é planejado.

```sh
# Keep the report for later
sizeledger analyze build/MyApp.ipa --out size/main.json

# Markdown in a GitHub Actions job summary
sizeledger analyze build/MyApp.xcarchive --format markdown >> "$GITHUB_STEP_SUMMARY"

# The ten biggest files anywhere in the bundle (bytes and file name)
jq -r '[.tree | .. | objects | select(has("children") | not)] | sort_by(-.bytes) | .[:10][] | "\(.bytes)\t\(.name)"' size/main.json
```

O formato do JSON está descrito no [artigo do DocC](https://muhittincamdali.github.io/sizeledger/documentation/sizeledgerkit/jsonlayout);
[Fixtures/snapshots](Fixtures/snapshots) tem relatórios completos.

## Os três tamanhos

| Tamanho                                            | Significado                                                                                 | Para o SampleShop 2.0 |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------- |
| Total (`bytes`)                                    | Os arquivos somados, o que um gerenciador de arquivos mostra                                | 8.75 MB               |
| Tamanho de instalação, estimativa (`installBytes`) | Cada arquivo arredondado para cima em blocos inteiros de 4 KiB, como o APFS armazena        | 8.80 MB               |
| Comprimido no `.ipa` (`compressedBytes`)           | O que os arquivos do bundle ocupam dentro do arquivo compactado; somente com entrada `.ipa` | 2.72 MB               |

Nenhum deles é o tamanho de download ou de instalação da App Store: a App Store adapta o app para cada
dispositivo (thinning), criptografa os binários e comprime o download. Esses números vêm do App Thinning
Size Report do Xcode e do App Store Connect. O sizeledger dá os que dá para obter só a partir dos
arquivos, em qualquer máquina e para cada build.
[Por que o tamanho de instalação é uma estimativa](docs/guides/why-install-size-is-an-estimate.md) traz
os detalhes, e [Limites de tamanho de App Clips](docs/guides/app-clip-size.md) os aplica aos App Clips.

## Como é testado

- **Contra o `du`**, a verificação de aceitação da v0.1, nas duas versões do SampleShop extraídas do
  `.ipa`. Em um Mac (Apple silicon, macOS 27.0.1, APFS), a estimativa de instalação é exatamente igual a
  `du -sk` e o total fica a menos de 0.16% de `du -A`; no contêiner Linux (swift:6.4.1-noble, aarch64),
  o total é igual a `du -b --apparent-size` e a estimativa de instalação fica a menos de 0.65% de
  `du -sk`, que lá também conta 4 KiB por pasta. Os testes falham acima de 1% nos dois.
- **Snapshots**: os relatórios JSON, de texto e Markdown das duas versões estão commitados; os mesmos
  snapshots passam no macOS e no Linux.
- **Um app de verdade**: o SampleShop é compilado com `swiftc`, `actool` e `codesign` por
  [um script](Fixtures/scripts/build-sample-app.sh) e roda no simulador do iOS 27.0:

    <picture><source media="(prefers-color-scheme: dark)" srcset="docs/media/sampleshop-ios27-simulator-dark.png"><source media="(prefers-color-scheme: light)" srcset="docs/media/sampleshop-ios27-simulator-light.png"><img src="docs/media/sampleshop-ios27-simulator-light.png" alt="SampleShop 2.0 no iOS 27 Simulator: um banner e uma lista de produtos com imagens e preços" width="240"></picture>

- **Leitores conferidos com referências**: o decodificador DEFLATE contra a saída do zlib para blocos
  stored, fixed e dynamic; o parser de Mach-O em arquivos thin, de 32 bits, fat e fat64; além de ZIP64,
  arquivos danificados e nomes de arquivo que contêm sequências de escape de terminal.

No total são 130 testes, executados pelo CI no macOS e no Linux (x86_64 e arm64). Medir o SampleShop 2.0
com o build release, incluindo a inicialização do processo, levou uma mediana de 14.4 a 17.4 ms em três
séries de 21 execuções, em um Mac (Apple silicon) ocupado com outro trabalho (carga média entre 41 e
136); o tempo depende do que mais a máquina está executando. [scripts/bench.sh](scripts/bench.sh)
repete a medição.

## Limites

- Os tamanhos são medições locais. Os tamanhos de download e de instalação da App Store dependem de
  thinning, criptografia e compressão feitos pela Apple, então o sizeledger informa uma estimativa e diz
  que é uma estimativa.
- Os asset catalogs (`Assets.car`) são contados como arquivos; as renditions dentro deles ainda não são
  listadas (planejado para a 0.8, por meio do `assetutil` no macOS).
- Os metadados do Swift são o tamanho das seções `__swift5_*`, um limite inferior: parte dos metadados
  fica em `__const`.
- Bundles no estilo iOS (iOS, iPadOS, tvOS, watchOS, visionOS) são classificados. Um `.app` de macOS com
  uma pasta `Contents/` é medido, mas seus arquivos caem em "Other resources".
- Um `.ipa` com mais de um app, entradas criptografadas, compressão diferente de stored e DEFLATE ou
  um caminho de entrada com um componente `..` é recusado com uma mensagem, sem adivinhação.
- Para chegar a um cabeçalho Mach-O no fundo de uma entrada comprimida de um `.ipa`, o sizeledger
  descomprime tudo o que vem antes e mantém só uma janela de 32 KiB; assim, uma entrada forjada
  custa tempo, não memória: cerca de 1 s por GB descomprimido em um Mac (Apple silicon).
- A entrada não é confiável, então uma entrada forjada ou corrompida não pode esgotar memória,
  tempo nem a pilha. O sizeledger recusa uma entrada com mais de 500.000 arquivos ou com um
  caminho aninhado além de 64 pastas, um `.ipa` que declara mais de 8 GiB de bytes não comprimidos
  e uma entrada `.ipa` que se descompacta para mais de 300 vezes o tamanho armazenado (uma bomba
  zip); aumente esses limites com `--max-files`, `--max-depth`, `--max-bytes` e `--max-ratio`.
  `--max-depth` vai até no máximo 100 para que o relatório JSON sempre possa ser escrito, e
  `--max-bytes` vale só para um `.ipa`, já que uma pasta não é descompactada. Cabeçalhos Mach-O ou
  ZIP malformados geram uma nota "unreadable" ou um erro claro com status de saída 2, nunca uma
  falha. Um caminho de entrada duplicado é contado uma vez.
