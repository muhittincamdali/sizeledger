Apunta sizeledger a un `.ipa`, un `.app` o un `.xcarchive` y te muestra dónde están los bytes de la app:
por categoría, por framework y recurso, por idioma y por arquitectura de CPU. Solo lee los archivos; no
compila, no ejecuta, no sube ni cambia nada, y funciona igual en macOS y en Linux.

<picture><source media="(prefers-color-scheme: dark)" srcset="docs/media/demo-analyze-dark.svg"><source media="(prefers-color-scheme: light)" srcset="docs/media/demo-analyze-light.svg"><img src="docs/media/demo-analyze-light.svg" alt="sizeledger analyze sobre SampleShop 2.0: 8.75 MB en 21 archivos, 8.80 MB de tamaño de instalación estimado, 2.72 MB comprimidos; catalog.json es el 70.8% de la app y Assets.car el 18.1%; siete idiomas; tres binarios universales con slices x86_64 y arm64"></picture>

<sub>Grabado con el comando real (<code>node scripts/demo.mjs</code>) sobre
<a href="Fixtures/README.md">SampleShop 2.0</a>, una app SwiftUI que este repositorio compila para el
iOS Simulator. La salida es la misma en un Mac (Apple silicon) y en las imágenes de CI de Linux.</sub>

## Lo más destacado

- **Una tabla para toda la app.** Ejecutable principal, frameworks y dylibs, extensiones de la app,
  App Clips, app de watch, localizaciones, asset catalogs, firma de código y todo lo demás. Las
  categorías siempre suman el total.
- **Cada framework y cada extensión en su propia línea**, y cada idioma `.lproj` sumado en toda la
  app y sus frameworks.
- **Slices de arquitectura de cada binario**: qué binarios son universales y cuánto ocupa cada slice;
  los tamaños de los segmentos y los metadatos de Swift van en el JSON.
- **Tres tamaños por separado**: lo que suman los archivos, una estimación del tamaño de instalación
  (bloques enteros de 4 KiB, como los guarda APFS) y, para un `.ipa`, el tamaño comprimido.
  sizeledger no afirma conocer el tamaño de descarga de la App Store;
  [aquí explicamos por qué](docs/guides/why-install-size-is-an-estimate.md).
- **Para personas y para CI**: una tabla en el terminal, Markdown para un pull request o el resumen de
  un job, y un informe JSON con un orden de claves estable que puedes versionar, procesar con `jq` y
  comparar.
- **También una librería de Swift**: [SizeLedgerKit](https://muhittincamdali.github.io/sizeledger/)
  da el mismo informe a tus propias herramientas. Sin dependencias: el lector de ZIP, el decodificador
  DEFLATE y el parser de Mach-O forman parte de ella.

## Inicio rápido

**1. Instala** (macOS o Linux con [Homebrew](https://brew.sh)):

```sh
brew install muhittincamdali/tap/sizeledger
```

Sin Homebrew, usa un
[binario de la release o compila desde el código fuente](#instalación).

**2. Mide tu app.** Sirve cualquiera de estos: un `.ipa` exportado, el `.app` de una compilación o un
`.xcarchive` de **Product › Archive**.

```sh
sizeledger analyze path/to/MyApp.ipa
```

**3. Lee la tabla.** "By category" dice qué tipo de contenido pesa más; "Largest items" nombra los
archivos, frameworks y carpetas; "Binaries" muestra cuáles llevan más de una arquitectura. Las notas del
final avisan cuando un número necesita contexto (por ejemplo, una compilación para simulador). Guarda el
informe completo con `--out size/main.json` para conservarlo o compararlo más adelante.

[Lee tu primer desglose](docs/guides/read-your-first-breakdown.md) recorre un informe real línea por
línea.

| `analyze` de un `.app`, `.ipa` o `.xcarchive`: categorías, componentes, idiomas, binarios y slices, árbol de archivos | funciona          |
| Salida como tabla de terminal, Markdown o JSON (`--format`, `--out`)                                                  | funciona          |
| macOS 13+ y Linux (x86_64 y arm64, Swift 6.2 y 6.4.1 en CI)                                                           | funciona          |
| Librería SizeLedgerKit con documentación DocC                                                                         | funciona          |
| `diff` de dos informes, con un resumen en Markdown para pull requests                                                 | planificado (0.2) |
| Reglas `budget` en YAML (por ruta, total, límite de App Clip) con código de salida 1, y una GitHub Action             | planificado (0.3) |
| Treemap en un solo archivo HTML; renditions de asset catalogs mediante `assetutil` en macOS                           | planificado (0.8) |
| Esquema JSON congelado (versión 1)                                                                                    | planificado (1.0) |
| Android `.apk` y `.aab`                                                                                               | planificado (1.1) |

Hasta que exista `budget`, comprobar un límite en CI es una línea de `jq`; consulta
[Comprobaciones de tamaño en CI](docs/guides/size-checks-in-ci.md).

## Instalación

| Método                  | Comando                                                                                                                                                                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Homebrew (macOS, Linux) | `brew install muhittincamdali/tap/sizeledger`                                                                                                                                                                                      |
| Binario de la release   | Descarga `sizeledger-<version>-macos-universal.tar.gz` o `-linux-x86_64` / `-linux-aarch64` desde [Releases](https://github.com/muhittincamdali/sizeledger/releases), compruébalo con `SHA256SUMS` y pon `sizeledger` en tu `PATH` |
| Desde el código fuente  | `git clone https://github.com/muhittincamdali/sizeledger.git && cd sizeledger && swift build -c release` (el binario es `.build/release/sizeledger`)                                                                               |
| Swift package           | `.package(url: "https://github.com/muhittincamdali/sizeledger", from: "0.1.9")`, producto `SizeLedgerKit`                                                                                                                          |

Para compilar hace falta Swift 6.2 o posterior (Xcode 26 o posterior en un Mac). Los binarios de Linux
incluyen el runtime de Swift y necesitan glibc 2.35 o posterior (Ubuntu 22.04, Debian 12 o más
recientes).

## Uso

```text
sizeledger analyze <input> [--format tty|markdown|json] [--out <file>] [--top <n>] [--color auto|always|never] [--quiet]
                    [--max-files <n>] [--max-bytes <bytes>] [--max-ratio <ratio>] [--max-depth <n>]
```

| Opción             | Qué hace                                                                       |
| ------------------ | ------------------------------------------------------------------------------ |
| `<input>`          | Una carpeta `.app`, un archivo `.ipa` o una carpeta `.xcarchive`               |
| `-f, --format`     | Qué imprimir: `tty` (por defecto, una tabla), `markdown` o `json`              |
| `-o, --out <file>` | Escribe además el informe JSON en un archivo; las carpetas que falten se crean |
| `--top <n>`        | Cuántos elementos, idiomas y binarios listar (por defecto 10)                  |
| `--color`          | `auto` usa colores solo en un terminal y no cuando `NO_COLOR` está definida    |
| `-q, --quiet`      | No imprime nada (junto con `--out`)                                            |

Código de salida: `0` cuando se generó el informe, `2` cuando no se pudo leer la entrada o escribir el
informe (una línea en la salida de error estándar explica el motivo) y `64` para opciones no válidas. El
`1` se reserva para el comando `budget` planificado.

```sh
# Keep the report for later
sizeledger analyze build/MyApp.ipa --out size/main.json

# Markdown in a GitHub Actions job summary
sizeledger analyze build/MyApp.xcarchive --format markdown >> "$GITHUB_STEP_SUMMARY"

# The ten biggest files anywhere in the bundle (bytes and file name)
jq -r '[.tree | .. | objects | select(has("children") | not)] | sort_by(-.bytes) | .[:10][] | "\(.bytes)\t\(.name)"' size/main.json
```

El formato del JSON se describe en el [artículo de DocC](https://muhittincamdali.github.io/sizeledger/documentation/sizeledgerkit/jsonlayout);
[Fixtures/snapshots](Fixtures/snapshots) contiene informes completos.

## Los tres tamaños

| Tamaño                                             | Significado                                                                                  | Para SampleShop 2.0 |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------- |
| Total (`bytes`)                                    | Los archivos sumados, lo que muestra un gestor de archivos                                   | 8.75 MB             |
| Tamaño de instalación, estimación (`installBytes`) | Cada archivo redondeado hacia arriba a bloques enteros de 4 KiB, como los guarda APFS        | 8.80 MB             |
| Comprimido en el `.ipa` (`compressedBytes`)        | Lo que ocupan los archivos del bundle dentro del archivo comprimido; solo con entrada `.ipa` | 2.72 MB             |

Ninguno es el tamaño de descarga o de instalación de la App Store: la App Store adapta la app a cada
dispositivo (thinning), cifra los binarios y comprime la descarga. Esas cifras las dan el App Thinning
Size Report de Xcode y App Store Connect. sizeledger da las que se pueden obtener solo a partir de los
archivos, en cualquier máquina y para cada compilación.
[Por qué el tamaño de instalación es una estimación](docs/guides/why-install-size-is-an-estimate.md)
da los detalles, y [Límites de tamaño de los App Clips](docs/guides/app-clip-size.md) los aplica a los
App Clips.

## Cómo se prueba

- **Contra `du`**, la comprobación de aceptación de la v0.1, con las dos versiones de SampleShop
  descomprimidas del `.ipa`. En un Mac (Apple silicon, macOS 27.0.1, APFS) la estimación de instalación
  es igual a `du -sk` y el total queda a menos de un 0.16% de `du -A`; en el contenedor de Linux
  (swift:6.4.1-noble, aarch64) el total es igual a `du -b --apparent-size` y la estimación de instalación
  queda a menos de un 0.65% de `du -sk`, que allí cuenta además 4 KiB por carpeta. Las pruebas fallan por
  encima del 1% en ambos.
- **Snapshots**: los informes JSON, de texto y Markdown de ambas versiones están versionados; los mismos
  snapshots pasan en macOS y en Linux.
- **Una app real**: SampleShop se compila con `swiftc`, `actool` y `codesign` mediante
  [un script](Fixtures/scripts/build-sample-app.sh) y se ejecuta en el simulador de iOS 27.0:

    <picture><source media="(prefers-color-scheme: dark)" srcset="docs/media/sampleshop-ios27-simulator-dark.png"><source media="(prefers-color-scheme: light)" srcset="docs/media/sampleshop-ios27-simulator-light.png"><img src="docs/media/sampleshop-ios27-simulator-light.png" alt="SampleShop 2.0 en el iOS 27 Simulator: un banner y una lista de productos con imágenes y precios" width="240"></picture>

- **Lectores comparados con referencias**: el decodificador DEFLATE con la salida de zlib para bloques
  stored, fixed y dynamic; el parser de Mach-O con archivos thin, de 32 bits, fat y fat64; y también
  ZIP64, archivos dañados y nombres de archivo que contienen secuencias de escape de terminal.

En total son 153 pruebas, que CI ejecuta en macOS y en Linux (x86_64 y arm64); una de ellas necesita
un nombre de archivo que no es UTF-8, que APFS rechaza, así que solo se ejecuta en Linux. Medir
SampleShop 2.0
con la compilación release, incluido el arranque del proceso, tardó una mediana de 14.4 a 17.4 ms en
tres series de 21 ejecuciones, en un Mac (Apple silicon) ocupado con otro trabajo (carga media entre
41 y 136); el tiempo depende de lo que más ejecute la máquina. [scripts/bench.sh](scripts/bench.sh)
repite la medición.

## Límites

- Los tamaños son mediciones locales. Los tamaños de descarga y de instalación de la App Store dependen
  del thinning, el cifrado y la compresión que se aplican en Apple, así que sizeledger informa de una
  estimación y lo dice.
- Los asset catalogs (`Assets.car`) se cuentan como archivos; las renditions que contienen aún no se
  listan (planificado para la 0.8, mediante `assetutil` en macOS).
- Los metadatos de Swift son el tamaño de las secciones `__swift5_*`, una cota inferior: parte de los
  metadatos está en `__const`.
- Los bundles al estilo iOS (iOS, iPadOS, tvOS, watchOS, visionOS) se clasifican. Un `.app` de macOS con
  una carpeta `Contents/` se mide, pero sus archivos van a "Other resources".
- Un `.ipa` con más de una app, entradas cifradas, una compresión distinta de stored y DEFLATE o una
  ruta de entrada con un componente `..` se rechaza con un mensaje, sin adivinar.
- Las rutas se comparan byte a byte, como las ven una herramienta de descompresión y un sistema de
  archivos: dos nombres que solo difieren en la normalización Unicode (NFC y NFD) son dos archivos,
  y una `/` seguida de una marca combinante sigue separando dos carpetas.
  Un nombre que no es UTF-8 válido se muestra leído como Latin-1, pero se sigue distinguiendo por
  sus bytes guardados: `caf\xE9.bin` y el `café.bin` en UTF-8 son dos archivos que se leen igual;
  el informe añade una nota cuando incluye un nombre así.
- Para llegar a una cabecera Mach-O situada muy adentro de una entrada comprimida de un `.ipa`,
  sizeledger descomprime todo lo anterior y solo conserva una ventana de 32 KiB, así que una entrada
  manipulada cuesta tiempo, no memoria: alrededor de 1 s por GB descomprimido en un Mac (Apple
  silicon).
- La entrada no es de confianza, así que una entrada manipulada o dañada no puede agotar la memoria
  ni la pila, y los límites que siguen acotan el tiempo que tarda. Un `.ipa` cuyas entradas
  comparten bytes almacenados (una bomba zip superpuesta) se rechaza como dañado. El `.ipa`
  manipulado más lento encontrado dentro de los límites predeterminados, de 28,6 MB con dos entradas
  que declaran 4,29 GB cada una y sus cabeceras Mach-O al final, tardó de 15 a 24 s en un Mac (Apple
  silicon) ocupado con otro trabajo; un `--max-bytes` más bajo reduce ese límite. sizeledger rechaza
  una entrada con más de 500 000 archivos o con una ruta anidada a más de 64 carpetas, un `.ipa` que
  declara más de 8 GiB de bytes sin comprimir y una entrada `.ipa` que se descomprime a más de 300
  veces su tamaño almacenado (una bomba zip); súbelos con `--max-files`, `--max-depth`,
  `--max-bytes` y `--max-ratio`. `--max-depth` llega como máximo a 100 para que el informe JSON
  siempre pueda escribirse, y `--max-bytes` solo se aplica a un `.ipa`, ya que una carpeta no se
  descomprime. Las cabeceras Mach-O o ZIP mal formadas dan una nota "unreadable" o un error claro
  con estado de salida 2, nunca un fallo. Una ruta de entrada duplicada se cuenta una vez.
